# 高频面试问答

## Q1：这个项目的核心价值是什么？

核心价值不是单点功能，而是把前端线上问题定位链路打通：从 SDK 采集，到服务端聚合，再到控制台展示和告警通知，尤其是把错误次数、影响人数和 Sourcemap 定位这些容易做错的口径真正统一起来。

## Q2：为什么要做成 Monorepo？

因为 SDK、Gateway、Console 三个应用共享一套事件模型和不少上下游契约。Monorepo 更适合统一类型、统一脚本、统一版本演进，减少跨仓库接口漂移。

## Q3：为什么客户端错误不能简单去重？

因为要区分“抑制刷屏”和“保留真实统计”。客户端可以做会话内短时防抖，但必须通过 `occurrences` 把真实次数恢复给服务端，否则服务端的 count、趋势图、告警都会错。

## Q4：为什么服务端不能按 fingerprint 去重？

因为 fingerprint 代表“同一类错误”，不是“同一条事件”。如果服务端按 fingerprint 去重，就会把真实复现的错误吞掉，直接破坏监控语义。

## Q5：为什么影响人数不能简单用 count 代替？

因为发生 100 次不代表影响了 100 个用户。一个用户死循环报错 100 次和 100 个用户各报 1 次，业务意义完全不同。所以必须单独统计去重 audience。

## Q6：现在的 affectedUsers 是怎么定义的？

优先按 `userId` 去重；如果业务没有传用户标识，就退化到 `session_id`。所以它更准确地说是受影响 audience 数。

## Q7：为什么 Replay 不放到错误详情表里一起存？

Replay 体积大、结构也完全不同。把它单独放在 `replay_sessions` 更合理，错误详情通过 `sessionId` 关联到 Replay。

## Q8：为什么 SDK 不上传 SourceMap？

因为 SourceMap 是构建产物，不是运行时事件。上传它更适合发布阶段，由 CI 调接口上传，SDK 只负责把 `release` 带出来。

## Q9：SourceMap 为什么一定要带 release？

因为只按文件名匹配在多版本并存时很容易串版本。`appId + release + artifact` 才是更稳定的定位键。

## Q10：现在 Sourcemap 具体能还原到什么程度？

当前可以还原主错误位置，也能返回源文件、行列号和源码片段。但还没有把整条 stack 的每一帧全部重写。

## Q11：为什么 Gateway 用 NestJS？

因为它适合做模块化的中后台服务，像鉴权、队列、定时任务、Swagger、依赖注入这些能力都比较顺手，适合当前项目的模块拆分。

## Q12：为什么要引入 Bull Queue？

为了把“上报接口低延迟返回”和“服务端复杂处理”拆开。HTTP 接口入队即可，Worker 慢慢消费，避免把写库、聚合、去重这些重操作堆在请求链路里。

## Q13：为什么选 PostgreSQL / TimescaleDB 而不是 Elasticsearch？

因为当前项目的核心是结构化时序聚合，不是全文检索。错误聚合、窗口统计、时间桶、去重 audience 这些查询，PostgreSQL 足够而且实现成本更低。

## Q14：Console 为什么用 React Query？

因为这是一个典型的数据查询型前端。React Query 可以统一处理缓存、重试、失效和加载态，比手写请求状态更稳。

## Q15：这个项目里你觉得最容易出错的地方是什么？

最容易出错的是统计口径。尤其是客户端防抖、服务端聚合、影响人数统计、错误详情和告警展示之间必须统一，否则每个页面都能看起来“有数据”，但其实都不可信。

## Q16：这个项目目前最大的边界是什么？

最大的边界是 SourceMap 还原目前还是单点定位，不是整条 stack remap；另外 Sourcemap 管理还没有对象存储和自动上传插件。

## Q17：如果继续演进，你会优先做什么？

我会优先做三件事：

1. 官方 CI 上传脚本 / 插件
2. 飞书 deeplink 到错误详情页
3. 完整 stack remap

## Q18：这个项目适合怎么包装成项目经历？

重点不要写成“做了一个监控后台”，而要强调：

1. 设计并打通浏览器 SDK、NestJS 网关和 React 控制台的数据链路
2. 解决错误防抖导致的服务端统计失真
3. 打通 SourceMap 源码定位和告警上下文能力
4. 修正多项目、多 session、多用户口径下的统计问题
