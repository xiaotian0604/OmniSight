# 技术面试问答

## 1. 为什么这个项目用 `pnpm workspace`？

### 简洁回答版

因为这是一个 Monorepo，而且上下游包之间有明确的 workspace 依赖关系。`pnpm workspace` 更适合统一依赖管理、共享内部包和跨包联调。它通过内容寻址和软链接机制减少重复安装，也更容易暴露依赖声明不规范的问题。对这种强契约项目来说，这是优点不是缺点。

### 压力追问方向

- `pnpm` 为什么更容易暴露幽灵依赖
- 和 `npm workspaces`、`yarn` 相比有什么差异
- 软链接机制对 Monorepo 有什么好处

## 2. `Turbo` 在这个仓库里具体解决了什么问题？

### 简洁回答版

`Turbo` 主要负责任务编排。比如根目录执行一次 `build`，它会按依赖关系先构建共享包，再构建 `sdk/gateway/console`，而不是我手动按顺序一个个跑。它的价值主要是统一入口、任务依赖管理和后续缓存扩展能力，适合这种多应用、多共享包的仓库。

### 压力追问方向

- 这个项目里有没有真正用到缓存
- 如果不用 Turbo，根脚本会怎么组织
- `Turbo` 和 `Nx` 的思路差异是什么

## 3. 为什么 SDK 选择 `Rollup` 而不是直接用 `Vite` 打包？

### 简洁回答版

因为 SDK 是一个要被不同业务项目消费的类库，而不是单一前端应用。`Rollup` 更适合类库打包，尤其是我要同时产出 `ESM`、`CJS` 和 `IIFE` 三种格式，并且对 external、tree-shaking 和产物结构有更细的控制。`Vite` 更偏应用开发体验，底层虽然也是 Rollup，但直接用 Rollup 更适合这个场景。

### 压力追问方向

- 为什么 SDK 需要三种格式同时存在
- 库打包场景下 external 的处理为什么更关键
- `IIFE` 场景为什么容易踩动态依赖的坑

## 4. `ESM / CJS / IIFE` 这三种产物分别解决什么问题？

### 简洁回答版

`ESM` 面向现代前端构建工具，最利于 tree-shaking；`CJS` 兼容一些 Node 或旧工具链的 require 场景；`IIFE` 适合最简单的浏览器直接 script 引入，比如纯 HTML 测试页。这个 SDK 的接入场景不止一种，所以三种都保留。代价是构建配置更复杂，不同格式下 external 和动态依赖处理要非常小心。

### 压力追问方向

- 为什么 `IIFE` 最容易暴露“看起来单文件，实际上不是单文件”的问题
- 为什么 `ESM` 更适合现代前端
- 什么时候可以只输出 `ESM`

## 5. `rrweb` 的本质是什么？它的优缺点是什么？

### 简洁回答版

`rrweb` 的本质不是录视频，而是录 DOM 快照和后续的交互事件，然后在回放端重建页面状态。所以它是“事件回放”，不是“屏幕录制”。优点是更适合做隐私处理和交互级定位，缺点是它依赖 DOM 环境重建，对 Canvas、跨域 iframe、非常复杂的动态页面会有天然边界。

### 压力追问方向

- 为什么说 rrweb 不是视频录制
- 隐私脱敏在 rrweb 里怎么做
- 为什么某些场景下回放会和真实用户页面存在偏差

## 6. 为什么要用 `web-vitals`，它适合做什么、不适合做什么？

### 简洁回答版

`web-vitals` 很适合采集 `LCP`、`CLS`、`TTFB`、`INP` 这类核心体验指标，因为这些指标有清晰标准，且和真实用户体验直接相关。它适合做体验层基线监控，但不适合替代更完整的性能分析，比如资源 waterfall、JS profile、内存分析这些它都不覆盖。所以我把它定位成“体验指标采集器”，不是“万能性能平台”。

### 压力追问方向

- `INP` 和 `FID` 的区别是什么
- `LCP` 为什么更能代表加载体验
- 为什么 Web Vitals 不能替代资源性能分析

## 7. 为什么上报链路里用 `fetch + keepalive`，而不是直接 `sendBeacon`？

### 简洁回答版

因为当前上报协议需要带 `x-api-key` 做鉴权，而 `sendBeacon` 不支持自定义 header。`fetch + keepalive` 既能带 header，又能在页面卸载时尽量完成发送，所以更适合这个场景。`sendBeacon` 的语义更适合 unload 上报，但能力边界也更严格。

### 压力追问方向

- `keepalive` 的边界是什么
- 为什么 `sendBeacon` 无法满足当前协议
- 如果既想用 `sendBeacon` 又要鉴权，可以怎么改协议

## 8. 为什么 Console 用了 `React Query`？

### 简洁回答版

因为这是一个典型的服务端状态驱动型前端。错误列表、错误详情、metrics、replay 都是查询型场景，`React Query` 能统一处理请求、缓存、失效、重试、加载态和错误态，比手写 `useEffect + useState` 更稳。它的缺点是概念比较多，如果 queryKey 和缓存策略不收敛，反而会把问题藏起来。

### 压力追问方向

- 什么叫服务端状态
- `staleTime`、`invalidate`、`queryKey` 在这个项目里分别起什么作用
- 哪些状态不适合放到 React Query

## 9. 既然用了 `React Query`，为什么还要用 `Zustand`？

### 简洁回答版

因为它们解决的是不同问题。`React Query` 负责服务端数据，`Zustand` 负责本地全局 UI 状态，比如当前选中的 `appId`、全局时间范围这类“会影响很多请求，但本身不是远程资源”的状态。这个项目里最典型的就是项目上下文和时间范围，它们不适合拿 React Query 管。

### 压力追问方向

- 为什么 `appId/timeRange` 更适合放 Zustand
- 为什么不用 Context 就够了
- Zustand 在非组件代码中可访问这一点有什么价值

## 10. 为什么 `queryKey` 一定要带 `appId`？

### 简洁回答版

因为这个控制台是多项目的，React Query 的缓存维度完全依赖 `queryKey`。如果错误详情、指标、Replay 这些查询的 key 没带 `appId`，切项目以后就会命中上一个项目的数据缓存，页面看起来请求成功了，但其实拿的是错项目的数据。这种 bug 最危险，因为它是静默错误。

### 压力追问方向

- 除了 `appId` 还要不要带时间范围
- 为什么只靠请求参数不够
- 你是怎么发现这个缓存串项目问题的

## 11. 为什么要单独封装 `apiClient` 和拦截器？

### 简洁回答版

因为这个项目有几个明显的横切点：统一 `/v1` baseURL、统一超时、自动注入 `appId`、统一错误处理。如果每个 API 调用点都自己做这些逻辑，重复代码会很多，而且非常容易漏。把它收敛到 `apiClient` 和拦截器里，项目上下文和错误处理策略就能统一。

### 压力追问方向

- 拦截器里适合做什么，不适合做什么
- 为什么过重的拦截器会让请求行为变得隐式
- 如果未来要加 token 刷新，这层怎么扩展

## 12. 为什么 Gateway 选 `NestJS`，不用 Express 直接写？

### 简洁回答版

因为这个服务端模块比较多，像鉴权、定时任务、队列、Swagger、SourceMap、告警、Replay、查询接口都需要清晰的模块边界。`NestJS` 在这种平台型服务里更适合，因为模块系统、依赖注入和生态插件都比较成熟。对这个项目来说，它的优势不是“更快”，而是“结构更稳、扩展更清楚”。

### 压力追问方向

- NestJS 的 DI 在这里到底带来了什么收益
- 模块化边界是怎么划的
- 如果这个项目很小，NestJS 会不会太重

## 13. 为什么会用 `class-validator` 做 DTO 校验？

### 简洁回答版

因为它和 NestJS 的 DTO 模型结合得很好，接口结构、校验规则和 Swagger 注释可以放在一起，Controller 层就能拿到清晰的输入边界。这个项目里像批量事件上报、SourceMap 上传这类接口都很适合这样做。缺点是它偏装饰器和 class 风格，复杂条件校验不一定是最轻的写法。

### 压力追问方向

- 为什么不直接用 Zod
- DTO 和领域模型是不是一回事
- 复杂校验应该放在哪一层

## 14. 为什么要用 `Bull + Redis` 做队列？

### 简洁回答版

因为上报链路是高频、短任务、需要削峰和重试的典型队列场景。`Bull + Redis` 集成成本低，和 NestJS 生态配合也不错，很适合当前规模。相比用数据库表模拟队列，它在任务状态、重试、延迟和消费模型上都更自然，也不会把业务数据库硬当消息中间件来用。

### 压力追问方向

- 为什么不用数据库表当队列
- Redis 队列的边界是什么
- 如果任务积压了应该看哪些指标

## 15. 为什么 Redis 的 `SET NX EX` 很适合做幂等和冷却？

### 简洁回答版

因为它简单、原子、成本低。`SET key value EX ttl NX` 可以在一个命令里同时完成“不存在才写入”和“自动过期”，很适合做事件级幂等保护和告警冷却位，不需要引入更复杂的分布式锁组件。对这个项目当前的粒度来说，这个方案是够用而且清晰的。

### 压力追问方向

- 为什么这是原子操作
- 幂等和分布式锁的边界在哪里
- 什么时候 `SET NX EX` 就不够了

## 16. 为什么数据层现在还是 `PostgreSQL / TimescaleDB`，不是 Elasticsearch？

### 简洁回答版

因为当前核心诉求是结构化时序聚合，不是全文检索。像错误率趋势、按 `fingerprint` 聚合、`SUM(occurrences)`、`COUNT(DISTINCT audience)` 这类查询，PostgreSQL 很适合，配合 TimescaleDB 的时间桶能力更自然。Elasticsearch 更适合全文检索和复杂日志搜索，但会引入额外的同步链路和运维复杂度。

### 压力追问方向

- 什么场景下 Elasticsearch 会更合适
- 为什么不是 ClickHouse
- TimescaleDB 在这里提供了什么价值

## 17. 为什么要在事件表里使用 `JSONB`？

### 简洁回答版

因为事件类型很多，但公共字段其实比较稳定。像 `app_id`、`session_id`、`type`、`ts`、`fingerprint` 这类字段适合结构化存储，而不同事件自己的细节字段差异很大，用 `payload JSONB` 存可以保留扩展性，不需要每加一种事件就大规模改表。原则是：高频筛选和聚合字段结构化，个性化字段放 JSONB。

### 压力追问方向

- 哪些字段必须结构化
- JSONB 建索引要注意什么
- 为什么不能一股脑全放 JSONB

## 18. 为什么 SourceMap 解析选 `@jridgewell/trace-mapping`？

### 简洁回答版

因为它足够轻、现代，而且核心 API 很直接，能满足我当前需求：根据编译后 `line/column` 找到原始源码位置，再从 `sourcesContent` 里提取代码片段。对这个项目来说，我真正需要的是稳定的 `originalPositionFor` 和源码内容读取能力，而不是一个更重的调试器体系。

### 压力追问方向

- 浏览器上报的列号和 SourceMap 查询列号口径有什么差异
- 为什么要做 basename 归一化
- 为什么 Sourcemap 匹配错了比解析失败更危险

## 19. 为什么要单独做 Vite 插件而不是只留一个上传接口？

### 简洁回答版

因为只有上传接口，业务方依然要自己解决 release 生成、HTML 注入、构建后扫描 `.map`、上传重试这些工程细节。Vite 插件把这些逻辑收口成一个统一入口，降低了接入成本，也让 release 和 Sourcemap 上传更不容易出错。接口是底层能力，插件是工程化交付形态，两者不能互相替代。

### 压力追问方向

- 插件做了哪些事情是接口本身做不了的
- 为什么还要保留 CLI
- 如果业务不是 Vite 项目，怎么复用同一套逻辑

## 20. 飞书 Webhook + HMAC 签名这套机制的优缺点是什么？

### 简洁回答版

优点是接入简单、耦合低，而且安全边界比较清晰。服务端只需要按飞书规则生成时间戳和 HMAC 签名，就能把消息推送到群里，不需要维护复杂的机器人长连接。缺点是它本质上还是单向通知，交互能力有限，而且签名和时间戳口径只要搞错，请求看起来发出去了，平台也会直接拒绝。

### 压力追问方向

- 飞书签名为什么容易被时间戳坑到
- HMAC 的输入到底是什么
- Webhook 和真正双向 Bot 的差别是什么
