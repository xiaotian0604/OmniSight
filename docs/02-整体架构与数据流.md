# 整体架构与数据流

## 1. 总体架构

```text
业务前端页面
  -> 注入 OmniSight SDK
  -> 采集 error / api / vital / resource / behavior / replay
  -> POST /v1/ingest/batch 或 /v1/replay

Gateway (NestJS)
  -> 鉴权
  -> 批量事件进入 Bull Queue
  -> Worker 异步去重、入库、聚合查询
  -> Query / Replay / Sourcemap / Alert 接口

Storage
  -> PostgreSQL / TimescaleDB: events, replay_sessions, sourcemaps
  -> Redis: 队列、事件级幂等去重、告警冷却位

Console (React)
  -> 调用 Query / Replay / Sourcemap 接口
  -> 展示概览、错误、性能、回放、SourceMap 管理页

Alert
  -> 定时扫描高频错误
  -> 反查 SourceMap
  -> 推送飞书卡片
```

## 2. 为什么拆成 SDK / Gateway / Console

### SDK

负责浏览器上下文里最贴近用户的采集逻辑：

- 事件监听
- session 管理
- 错误防抖
- 批量上报
- replay 录制

### Gateway

负责服务端统一接入和后处理：

- 鉴权
- 队列削峰
- 事件级幂等去重
- PostgreSQL 聚合查询
- SourceMap 反查
- 告警扫描和发送

### Console

负责查询结果的可视化：

- 概览
- 错误列表与错误详情
- replay 列表与播放器
- 性能页
- SourceMap 管理页

## 3. 错误事件的数据流

### 第一步：SDK 采集错误

错误来源：

1. `window.error`
2. `unhandledrejection`
3. `console.error`

SDK 会补齐：

- `appId`
- `sessionId`
- `ts`
- `url`
- `ua`
- `sdkVersion`
- `release`
- `fingerprint`

### 第二步：SDK 做会话内防抖

当前逻辑：

1. 同一个 `sessionId + fingerprint`，60 秒内首次错误立即上报。
2. 后续重复错误不立刻上报。
3. 被折叠的重复错误累计到 `occurrences`。
4. 60 秒到期或页面卸载时，补发聚合事件。

这一步的目标是：

- 防止循环报错把网络和服务端刷爆
- 又不丢真实错误次数

### 第三步：Gateway 接入与 Worker 入库

`POST /v1/ingest/batch` 接收事件后，不直接同步写库，而是：

1. 进入 Bull Queue
2. Worker 消费
3. 用 Redis 做事件级幂等去重
4. 写入 `events` 表

这里的去重不是按 `fingerprint`，而是按“事件级唯一身份”做幂等保护，避免破坏真实统计。

## 4. 为什么要有 `occurrences`

这是整个项目里最重要的统计口径设计之一。

如果 SDK 做了 60 秒防抖，但服务端仍按“事件行数”统计，就会出现：

- 用户明明同错触发了 10 次
- 数据库只有 1 行
- 高峰告警、错误次数、趋势图全部失真

所以现在的口径是：

- 事件行数不等于真实次数
- 真实次数 = `SUM(occurrences)`

## 5. 影响人数怎么统计

当前实现：

- 优先使用 `payload.userId`
- 没有 `userId` 时退化到 `session_id`

也就是说，当前字段名虽然叫 `affectedUsers`，但更准确的理解是“去重后的 audience 数”。

## 6. Replay 数据流

1. SDK 用 `rrweb` 录制用户操作。
2. 错误发生后，录制器等待错误窗口并上传 `/v1/replay`。
3. Gateway 保存到 `replay_sessions`。
4. Console 的 replay 列表页和播放器页读取回放数据。
5. 错误详情页通过 `sessionId` 查关联 replay。

## 7. SourceMap 数据流

1. 业务项目 CI 构建出 `.map` 文件。
2. CI 调 `POST /v1/sourcemap` 上传：
   - `appId`
   - `version`
   - `filename`
   - `mapContent`
   - Git 信息
3. SDK 上报错误时携带 `release`。
4. Gateway 查询错误详情或发送告警时：
   - 取 `appId + release + filename + lineno + colno`
   - 查 `sourcemaps` 表
   - 读取 `.map`
   - 还原源码位置和代码片段

## 8. 告警数据流

1. `AlertWorker` 定时扫描最近 N 分钟的高频错误。
2. 按 `appId + fingerprint` 聚合。
3. 用 `SUM(occurrences)` 计算真实次数。
4. 用 Redis 冷却位避免重复告警。
5. 调用 `SourcemapService` 还原源码位置。
6. 通过 `FeishuChannel` 发飞书卡片。

## 9. 关键设计取舍

### 为什么错误查询用 PostgreSQL 而不是 Redis

因为需要：

- 时间窗口过滤
- `GROUP BY fingerprint`
- `SUM(occurrences)`
- `COUNT(DISTINCT ...)`

这类查询天然适合 PostgreSQL。

### 为什么 SourceMap 不在 SDK 里上传

因为 SourceMap 是构建产物，不属于浏览器运行时职责。

合理流程应该是：

- SDK 只上报错误事件和 release
- CI 上传 SourceMap
- Gateway 反查

### 为什么 SourceMap 匹配要带 release

因为只按“最新同名文件”查找很容易串版本。

现在最可靠的匹配键是：

- `appId`
- `release`
- `artifact(filename)`
