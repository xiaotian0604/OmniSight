# 项目面试问答

## 1. 这个项目到底解决了什么问题？

### 简洁回答版

这个项目本质上不是一个中后台页面，而是一套前端可观测性链路。它解决了四类核心问题：浏览器侧如何稳定采集错误、性能、行为和回放；客户端为了防刷屏做防抖后，服务端怎么恢复真实错误次数；压缩代码报错如何精准定位到源码；以及告警如何从“只有一句错误文案”升级成“带源码位置、上下文和跳转入口”的可执行信息。

### 压力追问方向

- 为什么说这是“链路型项目”而不是“页面项目”
- 如果没有这套系统，团队排查线上问题最痛的点是什么
- 这个项目最有价值的设计决策是什么

## 2. 为什么要拆成 SDK、Gateway、Console 三个应用？

### 简洁回答版

因为这三部分的职责完全不同。SDK 负责浏览器运行时采集，重点是监听、防抖、session 和批量上报；Gateway 负责接入、异步消费、聚合查询、SourceMap 反查和告警；Console 负责把结果可视化。拆开后上下游边界更清楚，也更符合真实线上系统的部署方式。

### 压力追问方向

- 为什么 SourceMap 反查放在 Gateway 而不是 Console
- 如果以后再拆出独立告警服务，边界会怎么划
- 哪些字段是三端之间的强契约

## 3. 为什么这个项目适合放在 Monorepo 里？

### 简洁回答版

因为 `sdk`、`gateway`、`console` 共享同一套事件模型和不少关键字段口径，比如 `fingerprint`、`occurrences`、`release`、`affectedUsers`。这些字段一旦漂移，整条链路就会错。Monorepo 能把共享类型、构建脚本和版本演进统一起来，减少跨仓库接口漂移。

### 压力追问方向

- 如果拆成多仓库，最容易先出问题的是哪一层
- `packages/shared-types` 在这个项目里具体承担什么职责
- Monorepo 的成本和收益分别是什么

## 4. 你项目里最核心的一条数据链路是什么？

### 简洁回答版

最核心的是 `SDK -> Gateway -> Console / Alert` 这条链路。SDK 把错误、API、Vitals、Replay 采集上来；Gateway 做异步入库、错误聚合、SourceMap 反查和高频扫描；Console 展示错误详情和回放；Alert 把高频错误转成带源码上下文和 deeplink 的飞书消息。这条链路可信，项目才有价值。

### 压力追问方向

- 这条链路里最容易失真的地方在哪里
- 为什么 Replay 和错误详情要通过 session 关联
- 哪一层最容易成为性能瓶颈

## 5. 客户端错误防抖和服务端真实统计为什么会冲突？

### 简洁回答版

客户端防抖是为了防刷屏、防止循环报错打爆上报链路；但服务端统计的目标是保留真实业务语义。如果客户端把 60 秒内 10 次同错压成 1 条上报，而服务端又只按事件条数统计，那真实发生了 10 次的错误最终只会算成 1 次，错误率、Top 错误和告警阈值都会失真。

### 压力追问方向

- 为什么客户端必须防抖
- 为什么服务端不能简单把“收到几条就算几次”
- 如果用户 5 秒内关页，怎么保证累计次数不丢

## 6. `occurrences` 是怎么设计出来的？

### 简洁回答版

`occurrences` 是解决“客户端防抖后服务端统计失真”的补偿字段。现在同一个 `session + fingerprint` 在 60 秒内首次错误会立即上报，后续重复错误不会立刻发，而是在 SDK 内累计次数。等窗口结束或者页面卸载时，SDK 会补发一条聚合错误，带上 `occurrences=N`。Gateway 在错误列表、错误详情和告警扫描时统一按 `SUM(occurrences)` 算真实次数。

### 压力追问方向

- 为什么不把重复次数完全放到服务端推算
- 首条错误为什么还是要即时上报
- `occurrences` 和幂等去重之间怎么避免互相干扰

## 7. 为什么服务端不能按 fingerprint 去重？

### 简洁回答版

因为 `fingerprint` 代表的是“同一类错误”，不是“同一条事件”。如果服务端按 `appId + fingerprint` 去重，看起来数据更干净，但实际上会把真实复现的错误吞掉，直接破坏 `count`、`affectedUsers` 和高频告警。现在服务端只做“事件级幂等去重”，不做“错误语义去重”。

### 压力追问方向

- 当前幂等 key 怎么构成
- 为什么幂等和聚合是两件事
- 如果网络重试导致重复投递，系统现在怎么处理

## 8. 你现在说的“影响人数”到底是不是用户数？

### 简洁回答版

严格说它更准确地是“受影响 audience 数”。当前服务端统计逻辑是优先按 `userId` 去重，如果业务没有稳定用户标识，就退化成按 `session_id` 去重。所以在有用户体系的项目里它更接近真实用户数；没有用户体系时，它更接近受影响会话数。

### 压力追问方向

- `userId` 和 `sessionId` 的语义差别是什么
- 一个用户开两个 tab 算几个
- 为什么这个口径问题在监控系统里很重要

## 9. 为什么 Replay 不和错误详情直接存在一张表里？

### 简洁回答版

因为 Replay 数据体积大、结构和错误事件完全不同。错误事件适合放在统一的时序事件表里，Replay 更适合单独存 `replay_sessions`，通过 `sessionId` 去关联。这样既能保持错误查询轻量，也不会把大体积回放数据硬塞进错误详情链路里。

### 压力追问方向

- 为什么 session 是错误和回放的合理关联键
- 如果一个 session 里有多个错误怎么办
- Replay 上报为什么不能允许空 events

## 10. SourceMap 链路现在到底做到什么程度？

### 简洁回答版

现在已经打通了完整的版本化链路：构建阶段自动注入 `release`，构建后自动上传 `.map`，Gateway 在错误详情和告警时按 `appId + release + artifact` 精确命中 SourceMap，然后返回主错误的源码位置、源码片段，以及整条 stack 的结构化多帧 remap 结果。Console 会同时展示单点摘要、多帧栈和原始栈。

### 压力追问方向

- 为什么 `release` 是稳定主键
- 为什么要同时展示单点摘要和多帧栈
- 目前哪些栈格式还不能很好命中

## 11. 为什么 SDK 不负责上传 SourceMap？

### 简洁回答版

因为 SourceMap 是构建产物，不是运行时事件。浏览器拿不到完整构建产物清单，也不适合在用户运行时上传大体积 `.map` 文件，更有源码泄露风险。正确职责划分是：SDK 负责带 `release`，构建工具或 CI 负责上传 `.map`，Gateway 负责反查。

### 压力追问方向

- 为什么这件事必须属于发布链路
- 如果 CI 忘了上传 `.map`，系统会怎样降级
- 为什么 SourceMap 这类能力要和 release 强绑定

## 12. 为什么你还要额外做官方接入自动化？

### 简洁回答版

因为只有底层能力，没有接入自动化，项目仍然像 demo。现在补了 `@omnisight/build-tools`，提供 `Vite 插件 + CLI uploader`。Vite 插件会自动生成 release、注入到 HTML，并在构建完成后自动上传 JavaScript SourceMap；CLI 则作为非 Vite 场景和 CI fallback。这样业务方接入成本大幅降低。

### 压力追问方向

- 为什么先做 Vite 插件，不先做 Webpack 插件
- 插件和 CLI 的边界是什么
- 自动上传失败时为什么要默认让构建失败

## 13. 飞书告警现在为什么更“能用”了？

### 简洁回答版

因为它不再只是发一句错误文案。现在飞书卡片会带 `message / count / affectedUsers / 时间窗口 / release / 压缩后位置 / 源码位置 / 源码片段 / Git 信息`，并且还有 `错误详情页 deeplink`，有 Replay 的情况下还会带 `Replay deeplink`。收到告警的人基本可以直接点进去排查，而不是再手动搜日志。

### 压力追问方向

- 为什么 deeplink 对排障效率提升这么明显
- 为什么源码片段有价值，同时又有风险
- 告警消息里为什么还要保留压缩后位置

## 14. 你是怎么做告警冷却的？

### 简洁回答版

当前用 Redis 的 `SET key value EX ttl NX` 做冷却位。扫描到高频错误时会先抢占冷却位，避免同一错误短时间内重复通知。如果所有渠道都发送失败，就释放冷却位，让后续扫描还能继续发。这样既避免告警轰炸，也不会把“发送失败的告警”误当成已送达。

### 压力追问方向

- 为什么冷却位适合放 Redis，不适合放内存
- 为什么所有渠道失败时必须回滚冷却位
- 如果一个渠道成功、另一个失败，应该怎么记结果

## 15. 为什么错误详情接口主语义是 fingerprint，但还兼容 UUID？

### 简洁回答版

因为 Console 的路由主语义是 `fingerprint`，错误详情页面其实是在看“同一类错误”的聚合详情，而不是单条事件。但为了兼容一些内部或历史场景，我仍保留了按事件 UUID 查询的能力，只是在实现上做了收口：只有参数真的长得像 UUID 时才会按 `id` 查，否则一律按 `fingerprint` 查。

### 压力追问方向

- 之前这里出过什么 bug
- 为什么不能直接 try-catch 掉数据库异常
- 路由参数叫 `id` 会不会误导

## 16. 为什么 Gateway 适合做成异步入库？

### 简洁回答版

因为上报接口的目标是快返回，不应该同步承担写库、幂等、富化和后续扩展逻辑。现在 `POST /v1/ingest/batch` 只做校验和入队，Worker 再异步消费并写 PostgreSQL。这样 HTTP 请求链路和后处理链路被解耦，既能削峰也更便于后续扩展。

### 压力追问方向

- 如果不用队列，最先受影响的链路是哪段
- 队列积压时应该监控什么
- 幂等保护放接口层还是 Worker 层更合理

## 17. 你觉得这个项目里最有代表性的一个 bug 修复是什么？

### 简洁回答版

我觉得最有代表性的是“客户端防抖导致服务端统计失真”这条链路修复。表面现象是次数和影响人数不对，深层原因其实是 SDK 和 Gateway 都在用错误语义去重，双重叠加以后真实错误被严重压扁。最后我不是只改一个地方，而是重做了整条链路：SDK 会话级防抖 + `occurrences` 补偿，Gateway 改成事件级幂等，查询和告警统一按 `SUM(occurrences)` 聚合。

### 压力追问方向

- 你怎么验证这个修复是对的
- 为什么这是“修链路”不是“修单点”
- 修完后哪几个页面和模块必须一起回归

## 18. 这个项目现在还不能夸大的地方有哪些？

### 简洁回答版

有几个边界我不会说满：第一，虽然已经支持常见浏览器栈的多帧 remap，但还不是所有运行时格式的完整调试器级还原；第二，当前正式提供的是 Vite 插件和 CLI，不是完整的全栈构建生态插件；第三，Sourcemap 存储仍然是本地文件系统，不是对象存储；第四，WebSocket 实时告警还没有真正落地。

### 压力追问方向

- 为什么面试里必须诚实区分“做了”和“做了初级版”
- 哪些边界是架构问题，哪些只是工程完整度问题
- 如果继续做两周，你会先补哪一块

## 20. 如果继续演进，你下一步最想做什么？

### 简洁回答版

我下一步最想做三件事：第一，补 Webpack 官方插件，完善接入生态；第二，把 Sourcemap 存储升级到对象存储并加清理策略；第三，补 WebSocket 实时告警和更细的告警规则配置化。前两者是工程化和平台化，第三个是实时性和可运维性。
