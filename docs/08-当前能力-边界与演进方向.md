# 当前能力、边界与演进方向

## 1. 当前已经做成的能力

### 可用

1. 浏览器多类型事件采集。
2. session 级错误防抖和 `occurrences` 真实次数恢复。
3. 服务端错误聚合和影响人数统计。
4. Replay 上传、列表和播放器。
5. 错误详情与 replay 关联。
6. SourceMap 上传、查询和单点源码还原。
7. 飞书告警附带源码位置、源码片段和 Git 信息。
8. Console 的错误详情页展示源码上下文。

## 2. 初级版本或部分完成的能力

### SourceMap

当前状态：

- 已支持上传和反查
- 已支持 release 精确匹配
- 已支持代码片段
- 但不是整条 stack remap

### 性能分析

当前状态：

- API 和 Vitals 查询可用
- 资源维度还不完整

### 告警

当前状态：

- 飞书可用
- 冷却位逻辑可用
- 高峰统计口径已修正
- 但没有详情页 deeplink，也没有多渠道完整落地

## 3. 明确还没实现的能力

1. Vite / Webpack 官方 Sourcemap 上传插件
2. SourceMap 对象存储
3. 完整 stack trace 多帧 remap
4. 告警到 Console 的深链
5. WebSocket 实时告警
6. UA / Geo enrich 真正落地
7. 源码片段权限控制与脱敏

## 4. 面试时应该怎么诚实表达

### 可以说已经做了

- “已经打通了 SourceMap 上传、错误详情源码定位和飞书告警附带源码片段的链路。”
- “已经修复了客户端防抖导致服务端统计失真的问题，用 `occurrences` 恢复真实次数。”
- “已经把错误次数、影响人数和告警链路的统计口径统一起来。”

### 不要说得过满

- “支持完整源码还原和完整 stack 重写。”
- “有完善的实时告警系统。”
- “有生产级对象存储和发布插件。”

## 5. 后续演进建议

### 第一阶段

1. 做 CI 上传脚本 / 插件
2. 做飞书 deeplink
3. 做完整 Sourcemap 文档和接入模板

### 第二阶段

1. 做对象存储版 Sourcemap 管理
2. 做多帧 stack remap
3. 做更精确的资产映射（manifest 驱动）

### 第三阶段

1. 做 WebSocket 实时推送
2. 做告警规则配置化
3. 做资源性能与用户行为分析深化
