# OmniSight 项目总览与简历表述

## 1. 这个项目到底是什么

如果只用一句话介绍：

> OmniSight 是一个面向前端应用的全链路可观测性系统，我负责了从浏览器端 SDK 采集、服务端接入与聚合、到控制台可视化和告警链路的完整闭环。

如果再展开一点：

> 它解决的是“线上前端出了问题，但研发看不到用户现场”的问题。SDK 负责采集 JS 错误、接口耗时、Web Vitals、用户行为和错误现场回放；Gateway 负责异步接入、去重、聚合、查询和告警；Console 负责把错误趋势、聚合列表、错误详情和 rrweb 回放展示出来。

## 2. 你在简历里可以怎么写

### 版本 A：偏简洁，适合项目经历一页版

- 设计并实现基于 `pnpm + Turbo` 的前端可观测性 Monorepo，包含浏览器 SDK、NestJS Gateway、React Console 与共享类型包。
- 负责前端监控 SDK 的错误采集、接口监控、Web Vitals、用户行为埋点和 rrweb 错误现场回放能力。
- 设计服务端异步接入链路：`HTTP -> Bull Queue -> Redis 去重 -> PostgreSQL/TimescaleDB`，支撑错误聚合、时序指标查询和高频错误告警。
- 实现错误指纹聚合、`occurrences` 真实次数恢复、影响人数统计、SourceMap 关联和错误详情链路，提升问题定位效率。
- 开发 React 控制台，完成概览页、错误管理、回放页、性能页与 SourceMap 管理页。

### 版本 B：偏结果，适合面试时口述

- 我做的是一个“前端版 Sentry + Replay + Dashboard”的作品级系统，但我没有照搬现成方案，而是自己把采集、接入、聚合、告警和展示这几段完整打通。
- 技术上我重点解决了三个问题：
  - 浏览器端如何低侵入采集数据，同时避免错误风暴把链路打爆。
  - 服务端如何异步接入并恢复真实错误次数，而不是被客户端防抖误伤。
  - 控制台如何把“错误次数、影响人数、现场回放、上下文行为”拼成可定位的问题视图。

## 3. 30 秒自我介绍版本

> 我最近做了一个前端可观测性系统 OmniSight。它是 Monorepo 架构，包含一个浏览器 SDK、一个 NestJS Gateway、一个 React 控制台。SDK 会采集错误、API、Vitals、用户行为和 rrweb 回放；Gateway 用 Bull 和 Redis 做异步接入、去重和聚合；Console 负责展示错误趋势、错误详情和用户现场回放。我在里面重点处理了错误指纹聚合、客户端防抖下的真实次数恢复、影响人数统计和告警链路。

## 4. 3 分钟项目介绍版本

> 这个项目的背景是这样的：前端线上问题和后端不一样，很多时候日志里只有一句 “Cannot read property of undefined”，但是不知道用户当时点了什么、页面是什么状态、这个错误影响了几个人。所以我做了一个完整的前端可观测性闭环。
>
> 整体上它分三层。第一层是 SDK，跑在浏览器里，负责采集错误、接口请求、Web Vitals、资源性能、用户点击和路由变化；如果开启 replay，还会用 rrweb 在本地维护一个 Ring Buffer，在错误发生时只上传“错误前 30 秒 + 错误后 10 秒”的录像，避免把所有用户行为全量录上来。第二层是 Gateway，用 NestJS 写，负责接 SDK 的批量上报，把数据先写到 Bull Queue，再由 Worker 异步做 Redis 去重和 PostgreSQL/TimescaleDB 入库，这样可以把接入延迟压低。第三层是 Console，用 React + React Query + ECharts 做查询和展示，用户可以直接看到错误率趋势、Top 错误、错误详情、面包屑以及对应录像。
>
> 这个项目里我觉得最关键的不是把页面搭出来，而是把统计口径做对。因为 SDK 端为了防止循环报错会做 60 秒防抖，如果服务端直接按事件行数统计，就会把真实报错次数压扁。所以后来我引入了 `occurrences` 这个概念：客户端首条错误立即上报，窗口内重复错误只在内存里累计，超时或卸载时再补发聚合事件；服务端查询和告警全部按 `SUM(occurrences)` 聚合。这样既能保留防抖，又不会丢掉真实发生次数。
>
> 另一个重点是“影响人数”的口径。现在服务端优先按 `userId` 去重，没有 `userId` 时退化到 `sessionId`，所以它本质上是一个去重 audience 统计，而不是简单的事件次数。
>
> 这个项目比较适合展示我在浏览器端采集、Node 服务端、时序查询和可视化联调这几个方向的综合能力。

## 5. 你最值得强调的亮点

### 亮点 1：不是单点功能，而是闭环系统

面试时可以强调：

- 不是只做了一个 SDK，也不是只做了一个后台接口。
- 是“采集 -> 接入 -> 聚合 -> 查询 -> 展示 -> 告警”的完整链路。
- 这说明你不仅会写单个模块，还能处理系统边界和模块协作。

### 亮点 2：统计口径不是拍脑袋定的

你可以明确说：

- 错误次数不是简单 `COUNT(*)`
- 影响人数不是简单按事件行数算
- 客户端防抖和服务端真实统计之间有冲突，需要专门设计 `occurrences` 恢复机制

这会比“我做了错误监控系统”更有含金量。

### 亮点 3：能讲工程取舍

这个项目里可以讲清楚很多取舍：

- 为什么用 Monorepo
- 为什么接入层先入队再异步消费
- 为什么错误回放只在错误时上传
- 为什么客户端可以防抖，但服务端不能按 fingerprint 粗暴去重
- 为什么 SourceMap 要单独上传，而不是跟生产资源一起暴露在 CDN 上

## 6. 如果面试官问“这是作品项目还是线上项目”

建议实话实说：

> 这是一个我按真实生产问题去建模的作品级项目，重点不是业务量有多大，而是架构设计、链路打通和统计口径是否合理。我会明确区分哪些能力已经做成，哪些地方是为演示保留的简化实现。

这句话很重要。它既不虚，也不会把项目讲矮。

## 7. 你不要夸大的点

面试时不要直接说下面这些已经完整落地，除非你后续真的继续补完：

- “实时 WebSocket 告警已打通到控制台”
- “资源性能聚合图已经完整接入后端接口”
- “SourceMap 上传是生产级大文件上传方案”

更稳妥的说法是：

- 告警通道已经有服务端扫描与飞书发送链路，控制台实时推送预留了前端 store/hook，但当前主链路还是轮询查询 + 飞书通知。
- 资源采集已在 SDK 侧埋点，控制台资源聚合接口还未最终落地，因此页面目前明确展示为空状态。
- SourceMap 当前是 JSON 内容上传，更适合 demo/作品级闭环，生产环境会升级为 multipart 或对象存储直传。
