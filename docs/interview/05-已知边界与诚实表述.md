# OmniSight 已知边界与诚实表述

这份文档的目的不是“挑毛病”，而是帮你在面试里把话说稳。

## 1. 当前已经做成的能力

这些是你可以比较有底气讲出来的：

- 浏览器 SDK 采集错误、API、Vitals、资源、行为、白屏
- 基于 `fingerprint` 的错误聚合
- 基于 `occurrences` 的真实错误次数恢复
- 基于 `userId/sessionId` 的去重 audience 统计
- Bull + Redis + PostgreSQL/TimescaleDB 的异步接入链路
- rrweb 错误现场回放
- 错误列表、错误详情、趋势图、录像页
- SourceMap 上传记录与 Git 信息关联
- 高频错误扫描与飞书告警

## 2. 当前是简化实现，但逻辑闭环成立的能力

### 2.1 SourceMap 上传

当前状态：

- 使用 JSON body 上传 `mapContent`
- 服务端写本地文件系统

你可以这样讲：

> 这个版本重点是把 SourceMap 管理闭环跑通，所以用了 JSON 上传内容的简化实现。真实生产场景我会改成 multipart 或对象存储直传，因为大文件传输和稳定性会更好。

### 2.2 告警规则

当前状态：

- 规则比较简单，主要是按窗口内高频错误扫描
- 冷却控制已经有
- 高级规则引擎还没做

可以这样讲：

> 当前告警链路已经把“扫描、控频、发送”跑通，但规则系统还是偏简化版，后续可以继续拆成高频、高影响面、错误率突增等多维规则。

## 3. 当前还没有完整落地，不要硬说成已完成的能力

### 3.1 控制台实时 WebSocket 告警

当前状态：

- 前端有 `useWebSocket` 和告警 store
- 但 Gateway 里没有完整的 WebSocket 推送网关落地
- 当前主要告警出口还是飞书

正确说法：

> 我预留过控制台实时告警的前端接收层，但当前稳定可用的主链路是服务端扫描 + 飞书通知。

错误说法：

> 我已经做完实时 WebSocket 告警系统。

### 3.2 资源性能聚合图

当前状态：

- SDK 端有资源采集
- 但控制台资源聚合接口还没完全落地
- 页面现在已经改为空状态，不再展示假数据

正确说法：

> 资源采集埋点已经有，资源聚合展示这块我做了留口，但当前正式展示的重点还是 Vitals 和 API 指标。

### 3.3 生产级大规模部署能力

当前状态：

- 架构思路是对的
- 但没有必要夸成高并发生产平台

正确说法：

> 这个项目重点是完整链路设计和工程实现，不是大规模生产流量证明。

## 4. 你可以主动承认的工程边界

面试里主动说出边界，反而会显得判断力更强。

你可以直接说：

- 当前事件富化（UA、GeoIP）还留在 Worker 的预留点，没有完整落地。
- SourceMap 目前按文件名关联 Git 信息，版本级精确匹配还可以继续加强。
- 全量 SDK 测试并不是全部完美，当前我更重视关键链路的构建验证和定向测试。

## 5. 一句很稳的收尾说法

> 这个项目我会把“已经落地的能力”和“有设计但仍是简化实现的部分”区分开讲。我的目标不是把项目吹成现成商业产品，而是证明我能独立设计一套前端可观测性链路，并且知道哪些地方是工程现实里的关键问题。
